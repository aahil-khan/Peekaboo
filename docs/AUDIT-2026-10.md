## 1. Verdict

**The code is in better shape than the product.** The overlay is polished, the
plugin system is thoughtful, the Rust side has real tests and honest comments.
What is missing is a reason to install it, and that is a positioning problem,
not an engineering one.

Today Peekaboo's loop is: hotkey → type a question → read the answer → `Alt+C`
→ paste it somewhere. A pinned browser tab's loop is: alt-tab → paste → read →
copy → alt-tab → paste. Peekaboo saves two keystrokes. Nobody installs a desktop
app, grants it screen and clipboard access, and runs it at login to save two
keystrokes. That is the whole reason it stalled.

The things that would make it worth installing are exactly the ones marked
"not yet implemented" in the code: **acting on what is selected, and writing the
answer back**. Everything else in this document follows from that.

Three decisions, up front:

1. **Do not try to replace Raycast or PowerToys.** They are launchers and
   utility suites with years of surface area (app search, clipboard history,
   window management, snippets, calculator, extension stores). A weaker
   launcher never displaces a stronger one. Peekaboo should sit *beside*
   whatever launcher the user already has and own one thing they do not do
   well on all three OSes: AI on the thing you are looking at.
2. **Reposition from "AI chat overlay" to "AI action layer".** Select text
   anywhere → hotkey → pick or type an action → result appears → `Enter`
   replaces the selection, `Alt+C` copies, or you keep talking. Screenshot and
   free-form chat remain, as the second and third loops.
3. **Beachhead on Linux, ship Windows second, macOS third.** Linux has zero
   commercial competition in this space and the most tolerant early adopters.
   Build the platform layer for all three from day one, but earn the first
   users where nobody else is.

## 4. Value proposition and beachhead

### Who (beachhead)

Developers and technical writers on **Linux desktops (GNOME and KDE)** who already
run Ollama or hold an API key, and currently keep a ChatGPT/Claude tab pinned.

Why this segment first:

- **Burning pain:** no native tool exists; alt-tab to a browser is the status quo.
- **Willingness to adopt:** they install from GitHub Releases, Flathub and AUR
  without blinking, and run things at login.
- **Winnable:** zero commercial competitors on Linux; one OSS competitor with
  a weaker UI.
- **Referral:** r/linux, r/LocalLLaMA, HN, Fedora/Arch forums, awesome-lists and
  YouTube "Linux desktop setup" channels are strong word-of-mouth loops.

Expansion: Windows power users who already run PowerToys and want AI beyond
clipboard-paste; then macOS, where Raycast/Writing Tools make it hardest.

### Value proposition (6-part)

1. **Who:** keyboard-first developers and writers on Linux who use an LLM many times a day.
2. **Why:** fix, explain, translate, rewrite or ask about *the thing in front of them* without leaving it.
3. **What before:** select → copy → alt-tab → paste into a tab → read → copy → alt-tab → paste back. Every single time.
4. **How:** select text (or a screen region) → one hotkey → pick an action or type a question → the result lands back in the app, or in the clipboard, or you keep talking. Any model, including fully local.
5. **What after:** the model is a keystroke away in every app, with no context switch and nothing leaving the machine unless they choose.
6. **Alternatives:** browser tab (slow loop), Writing Tools (rewrite only, no conversation, no screen), launcher plugins (chat in a list), Cherry Studio (Electron, heavy).

**Statement:** For developers and writers on Linux who reach for an LLM all day,
Peekaboo is an AI action layer that works on whatever you have selected, from any
app, with any model. Unlike a browser tab or a launcher plugin, the answer goes back
where the text came from.

Marketing one-liner: *Select anything. Hit one key. The answer lands where you were.*

## 5. The product: three loops and an actions palette

### Loop 1 — Act on selection (the headline, currently missing)

1. User selects text in any app and presses the hotkey.
2. Overlay opens **with the selection already attached** and an **actions palette**
   showing: Fix grammar, Rewrite, Make shorter, Explain, Translate to…,
   Summarise, Reply to this, Explain code, Add comments, Convert to… plus any
   user-defined actions (name + prompt template, stored in settings).
3. Result streams into the overlay. `Enter` **replaces the selection** in the
   source app (type-back or paste-back), `Alt+C` copies, typing continues the
   conversation.

This is what WritingTools, Apple Writing Tools, Raycast AI Commands and Kerlig
all converge on, because it is the loop that beats the browser tab.

### Loop 2 — Ask about the screen

Already exists on Linux via the portal. Needs Windows and macOS region capture,
and a hotkey that opens the overlay *with the capture already attached* rather
than requiring the overlay to be open first.

### Loop 3 — Ask anything

The current product. Keep it as the fallback when nothing is selected.

### What to cut or demote

- **"Memories" as named.** Either rename to **Snippets** (which is what it is) or
  make pinned memories actually reach the system prompt. Doing the second turns a
  confusing feature into a real one for little effort.
- **llama.cpp process management in the wizard.** Powerful, but it is the most
  complex path in onboarding and the smallest audience. Keep in Settings, drop
  from the first-run wizard.
- **System Resources plugin** as a bundled default. Fine as an example plugin,
  weak as a headline. Replace in the README with the actions palette.
- **The stale build plan** (`docs/build plan.md`): React 18, shadcn, xcap, none
  of which the code uses. Delete or rewrite.

### Plugin system direction

The four plugin types already map onto the new model: `input` = auto-context,
`context` = `/` sources, `output` = post-processors, `model` = backends. Add a
fifth, **`action`**, which is a prompt template plus optional pre/post hooks,
and make user-defined actions a trivial no-code form in Settings that writes the
same manifest. That gives the "extensions" story Raycast users expect without
building an app store.

## 7. Technical findings (ranked)

### 7.1 Ollama unloads the model five seconds after every answer — `src/providers/ollama.ts:74`

`keep_alive: "5s"` tells Ollama to evict the model 5 s after the response. Every
question therefore pays a cold load (seconds for a 7–8B model). This single line
contradicts "instant" for the default, local-first provider. Make it a setting;
default to Ollama's own default (`5m`) or longer.

### 7.2 Anthropic provider: paid request every 5 seconds, stale models, CORS — `src/providers/anthropic.ts`, `PeekSurface.tsx:~530`

- `isAvailable()` POSTs a real `/v1/messages` call. `PeekSurface` polls
  `isAvailable()` **every 5 seconds whether or not the overlay is visible**.
  With Anthropic selected that is ~17,000 billed requests per day.
- The probe uses `claude-3-haiku-20240307`, a retired model, so it returns 404,
  not 400, and the footer permanently says "check your API key".
- Browser-origin requests to Anthropic require the
  `anthropic-dangerous-direct-browser-access: true` header or they fail CORS.
  The webview enforces CORS, so streaming is almost certainly broken too.
  (Not verified live; no key available during the audit.)
- `models()` is a hardcoded 2024 list. Anthropic has a `/v1/models` endpoint.
- OpenAI's filter (`gpt-`, `o1-`, `o3-`) and Gemini's `isVision: true` for every
  model are the same class of staleness.

Fix: route through `tauri-plugin-http`; poll availability only while visible
and only with a cheap GET (`/v1/models`); fetch model lists live; cache.

### 7.3 Hotkey conflicts (see §6)

`Ctrl+Space` globally breaks IntelliSense in VS Code, JetBrains, Vim completion
and Emacs mark, and is IME switching on Windows/macOS. `Alt+Space` is the Windows
window menu and PowerToys Run. Both are the worst possible defaults for the
target user, and neither can be changed.

### 7.4 "Memories" never reach the model — `MemoryOverlay.tsx`, `markdown.tsx`

Memories are saved, pinned, searched and inserted into the input on Shift+Enter.
No code path adds them to `streamPayload`. Users will assume the model remembers
and be wrong. Rename to Snippets, or inject pinned items into the system prompt.

### 7.5 Plugin scoping is bypassable — `src/lib/plugins/registry.ts:60`

Plugins load via `import(data:…)` into the **main webview**. They share
`window.__TAURI_INTERNALS__` and can call `invoke` directly: `plugin_read_file`
with any `pluginId`, the `sql` plugin (whole chat history), clipboard,
`launch_llama_server` (arbitrary binary execution with arbitrary args). The
README says "a real boundary, not a sandbox", but the per-plugin fs scoping is
decorative when the plugin can name any id. Either run plugins in a sandboxed
`<iframe sandbox>` or Worker with a postMessage bridge that injects the id, or
remove the claim and say "plugins are trusted code".

### 7.6 API keys in plaintext `localStorage` — `src/store/settings.ts`

Any plugin, and any process that can read the WebKit local-storage directory,
gets every key. Move to the OS keychain.

### 7.7 Images stored inline in `messages.content`

Attachments are JSON-serialised base64 inside the message row. One screenshot
per question grows the DB by ~1 MB each. Store blobs in a separate table or on
disk and reference them.

### 7.8 Smaller items

- Cold-start check: `plugin_get_selection` spawns `wl-paste` then `xclip` on
  every send (`lib.rs:76`). Cheap, but sits on the hot path and is silent on failure.
- `launch_llama_server` runs any binary path from the frontend with any args.
  Fine for a trusted frontend; dangerous combined with §7.5.
- `commands::hide_peek` resets height to 80 while `tauri.conf.json` says 86 and
  the comment in `PeekSurface` says 86.
- Two empty tracked files at repo root: `tauri` and `peekaboo-app@0.1.0`.
  Untracked: `peekaboo-app.png`, `.playwright-mcp/`.
- `docs/build plan.md` describes a different app (React 18, shadcn, xcap).
- The uncommitted panel-scoping change (`PeekSurface.tsx`, `index.css`) typechecks
  and reads correctly. Commit it.
- No frontend tests at all. The provider stream parsers (SSE buffering, NDJSON)
  and the slash-menu state machine are the obvious first targets.
- No CI. A GitHub Actions matrix running `tsc`, `cargo test` and `tauri build`
  on three OSes would have caught the `HOME` and stub issues already.

### 7.9 Test run

`cargo check --tests`: clean. `cargo test --lib`: 21 tests, 19 passed, 0 failed,
2 ignored (the home-directory search budget and the real-PDF test, both opt-in).

## 8. Roadmap

Ordered so each phase ships something a user can feel. Estimates are for one
person working evenings; halve them with a worker per task.

### Phase 0 — Stop the bleeding (1 week)

- `keep_alive` setting, default `5m`.
- Availability polling only while visible, GET-only, 30 s interval.
- Anthropic: live `/v1/models`, current probe model, route via `tauri-plugin-http`.
- Configurable hotkey with per-OS defaults (`Super+Space`-style chords avoid most conflicts; let the user pick).
- Rename Memories → Snippets *or* inject pinned ones into the system prompt.
- Quit in the legend/footer. Commit the WIP. Delete stray files and the stale plan.
- GitHub Actions: `tsc` + `cargo test` + `tauri build` matrix on ubuntu/windows/macos.

### Phase 1 — Platform layer (3–4 weeks)

- Paths via Tauri `path()` APIs. Fix Windows `HOME`.
- Selection read on all three OSes with clipboard fallback and restore.
- Type-back / paste-back on all three OSes (`enigo` + Wayland portal).
- Region capture on Windows and macOS.
- Active window title/app on all three (best effort on Wayland).
- Portal-based global shortcut on Linux with X11 fallback.
- Keychain storage for API keys.

### Phase 2 — The action layer (3 weeks)

- Overlay opens with selection attached and an actions palette.
- ~10 built-in actions as `action` plugins; user-defined actions in Settings.
- `Enter` replaces selection; `Alt+C` copies; typing continues.
- A "capture then ask" hotkey that opens the overlay with a region already attached.
- Plugin sandbox (iframe/Worker bridge) *or* drop the scoping claim.

### Phase 3 — Distribution (2 weeks, then ongoing)

- Signed builds: Apple Developer ID + notarisation, Windows code-signing.
- `tauri-plugin-updater` against GitHub Releases.
- Flathub, AUR, winget, Homebrew cask.
- README rewritten around the three loops, 20-second GIF of Loop 1.
- Launch posts: r/linux, r/LocalLLaMA, HN Show, Fedora/KDE forums.

Do not start Phase 3 before Phase 2. Shipping the current loop to more
platforms gives you the same non-install reason on three OSes instead of one.

## 9. Open questions for you

1. Are you willing to pay for an Apple Developer account (~$99/yr) and a Windows
   signing cert? Without them, macOS and Windows distribution is a dead end
   regardless of code quality.
2. Is "replace the selection" acceptable as paste-back (clipboard + simulated
   `Ctrl/Cmd+V`) for v1, or do you want true character typing from day one?
3. Do you want to keep the plugin fs-scoping claim and build the sandbox, or
   drop it and call plugins trusted code? Both are defensible; the current
   middle is not.
4. Which second OS do *you* use enough to dogfood: Windows or macOS? Dogfooding
   beats the market argument.
